# Spec: Cart checkout, status polling, and end-to-end demo

- **Status:** APPROVED (owner request, 2026-09-29: path `/v1`, JWT + ownership, browser-side webhook simulator, camelCase; money as `amount` decimal string + `amountMinor`; revised same day: cart items priced by the backend, mock gateway page, frontend return + webhook, debug events endpoint)
- **Owner (human):** Thapanut L.
- **Related:** ADR-0002, ADR-0003, specs [2c2p-payment-webhook](2c2p-payment-webhook.md) and [payment-events-outbox](payment-events-outbox.md), flow [frontend-integration-flow](frontend-integration-flow.md), contracts `listProducts`, `createPayment`, `getPaymentStatus`, `getDemoPaymentEvents`, table `payments`
- **Size:** M

## 1. Goal
Let a browser check out a cart with 2C2P and follow the payment to its final status, so the whole flow (cart → create → 2C2P page → frontend return + webhook → outbox/Kafka → status) can be run locally from one page. Success metric: a payment created from the demo page shows SUCCESS or FAILED within one poll (≤ 2 s) of the webhook being accepted.

## 2. Scope
- In: `GET /v1/products`, `POST /v1/payments` (cart items, priced by the backend), `GET /v1/payments/{invoiceNo}/status`, `GET /v1/demo/payments/{invoiceNo}/events` (demo only), outbound ports `ProductCatalog` (sample static catalog) and `PaymentGateway` (**stub** 2C2P adapter), `OutboxRepository.ListByKey`, migration `0003_payment_checkout`, a static demo page at `GET /demo` and `GET /demo/return` behind `DEMO_UI_ENABLED`, `make demo`.
- **Out of scope:** the real 2C2P Payment Token API call and hosted page, persisting order lines, a product/pricing service, payment expiry, a second attempt reusing a PENDING payment, rate limiting, the Angular frontend.

## 3. Design notes (from Architect)
Full flow with the webhook and the outbox: [frontend-integration-flow.md](frontend-integration-flow.md).

- **The client never sends an amount.** It sends `orderId` and `items` (`productId`, `quantity`); `CheckoutService` prices them through the `ProductCatalog` port (`domain.PriceOrder`: catalog price × quantity, `int64` overflow-checked, one currency) and returns the priced lines. The sample catalog (3 products, THB) stands in for a pricing service. Lines are returned, not stored.
- `CheckoutService` (inbound port `CheckoutUseCase`) creates the payment `PENDING` in one transaction, **then** asks `PaymentGateway` for a payment session. The payment row exists before 2C2P can know its invoice number, so a webhook can never arrive for an unknown invoice.
- The gateway call is outside the DB transaction (no network I/O while holding a transaction). If it fails, the payment stays `PENDING` without a session and the client gets 500 (AC-05).
- `invoiceNo` is generated by the server (`INV` + 32 hex chars from a UUID) and is the reference shared with 2C2P. `orderId` is the caller's order reference and is stored, not used as the invoice number, so each attempt for one order has its own invoice.
- Money on the wire: `amount` (and `price`, `unitPrice`, `lineTotal`) is the decimal string a person reads ("1000.00"); `amountMinor` (responses only) is the same value in satang (100000) for arithmetic. A bare integer named `amount` next to `currency` reads as 100,000 THB, so minor units always carry the `Minor` suffix. The backend parses the decimal with string arithmetic (`domain.ParseDecimal`), never float, and stores `int64` minor units.
- Ownership: the payment stores the JWT subject as `customer_id`. The status endpoint returns `NOT_FOUND` for another customer's payment, identical to an unknown invoice (no enumeration).
- The stub gateway returns `paymentToken` = `stub_<32 hex>` and `checkoutUrl` = `https://checkout.2c2p.invalid/payment/<token>` (`.invalid` is a reserved TLD, so the URL can never be mistaken for a real one). It is replaced by a real Payment Token API adapter in a later spec.
- Demo page: one static HTML file embedded in the binary, served at `/demo` (shop) and `/demo/return` (the frontend return URL) only when `DEMO_UI_ENABLED=true`. It plays both the browser and 2C2P: a modal stands in for the hosted payment page; on "pay" it performs the **two callbacks** of the real gateway: the frontend return (navigate to `/demo/return?invoiceNo=…`, which shows *Verifying…* and polls every 2 s, never trusting the redirect) and, 3 s later, the server-to-server webhook signed in the browser (WebCrypto HMAC-SHA256) with a secret it receives in the URL **fragment** from `make demo`. The backend never sends the 2C2P secret to a client.
- Debug view: `GET /v1/demo/payments/{invoiceNo}/events` (JWT, owner only, registered only with `DEMO_UI_ENABLED=true`) lists the payment's outbox rows (by `message_key` = payment id; unindexed scan, diagnostics only) with `publishedAt`, and says where the relay publishes (`kafka`, `in-process`, `disabled`), so the page can show whether the event really reached Kafka.

## 4. Contract / schema
- Uses: `listProducts`, `createPayment`, `getPaymentStatus`, `getDemoPaymentEvents` (new), `receive2c2pPaymentNotification` (unchanged), table `payments`
- **Changes (approved with this spec):**
  - `contracts/openapi.yaml`: tags `payments`, `demo`, the four operations, schemas `CreatePaymentRequest` (items, no amount), `Product`, `OrderLine`, `PaymentCheckout`, `PaymentStatus`, `DemoPaymentEvents`, `DecimalAmount`, `AmountMinor`, `Currency`.
  - `contracts/asyncapi.yaml` (unreleased, no consumers yet, so changed in v1): `payment.status-changed` carries `amount` as a decimal string and adds `amount_minor` (integer minor units); previously `amount` was the integer minor units.
  - Migration `0003_payment_checkout`: `payments.order_id text NOT NULL DEFAULT ''`, `payments.customer_id text NOT NULL DEFAULT ''`. Backward compatible: rows created by earlier versions get `''` and belong to no customer.
  - Env `DEMO_UI_ENABLED` (default `false`).

## 5. Acceptance criteria
| ID | Given | When | Then |
|---|---|---|---|
| AC-01 | A customer with a valid bearer token | `POST /v1/payments` with `{"orderId":"ORD-1","items":[{"productId":"COFFEE-BEANS-250G","quantity":1},{"productId":"CERAMIC-MUG","quantity":1},{"productId":"POUR-OVER-DRIPPER","quantity":1}]}` | 201 with `invoiceNo`, `orderId`, `status` PENDING, priced `lines`, `amount` "1000.00", `amountMinor` 100000, `currency`, `paymentToken`, `checkoutUrl`; the payment is stored PENDING with the order id and the token's subject as owner |
| AC-02 | A valid bearer token | The body is malformed, has unknown fields (including `amount` or a per-item price), misses `orderId` or `items`, `orderId` is not 1–64 of `[A-Za-z0-9_-]`, `items` is empty or has more than 20 entries, a `quantity` is not an integer 1–99, a `productId` repeats or is unknown | 400 `VALIDATION_ERROR`; nothing is stored |
| AC-03 | No, expired, or forged bearer token | Either endpoint is called | 401 `UNAUTHORIZED` |
| AC-04 | A customer | Creates two payments for the same `orderId` | Two different `invoiceNo`s; both PENDING |
| AC-05 | The payment gateway fails | `POST /v1/payments` | 500 `INTERNAL_ERROR` with no internal detail; the payment stays PENDING |
| AC-06 | The customer owns payment `INV…` | `GET /v1/payments/INV…/status` | 200 with `invoiceNo`, `orderId`, `status`, `amount`, `amountMinor`, `currency`, `updatedAt` |
| AC-07 | Payment `INV…` belongs to another customer, or does not exist | `GET /v1/payments/INV…/status` | 404 `NOT_FOUND`, same body for both cases |
| AC-08 | A payment created through `POST /v1/payments` | A validly signed 2C2P webhook for its invoice is processed | The status endpoint returns SUCCESS (or FAILED) |
| AC-09 | Any | A checkout request is logged | The log has the route template and trace id; no order id, invoice number, or payment token |
| AC-10 | `DEMO_UI_ENABLED` unset or `false` | `GET /demo`, `GET /demo/return`, or `GET /v1/demo/payments/{invoiceNo}/events` | 404 `NOT_FOUND`; with `true` the pages are served as `text/html` with a restrictive CSP |
| AC-11 | `DEMO_UI_ENABLED=true` | The demo page is fetched | The response contains no secret (JWT or 2C2P key) |
| AC-12 | A valid bearer token | `GET /v1/products`, then a cart of 2 × beans (450.00) + 1 × mug (290.00) is checked out | Products carry `price`/`priceMinor`/`currency` from the catalog; the payment amount is 1,190.00 THB, computed by the backend |
| AC-13 | `DEMO_UI_ENABLED=true`, the customer's payment was settled by a webhook | `GET /v1/demo/payments/{invoiceNo}/events` | 200 with `publisher` and the one `payment.status-changed` outbox event (`publishedAt` null until the relay publishes it); another customer gets 404; no token gets 401 |

## 6. Non-functional
- Performance: create = one insert + one gateway call; status = one indexed read by `invoice_no`. p95 < 300 ms excluding the real gateway.
- Security / PII: all `/v1` routes require a bearer token; ownership check on read; strict JSON decoding; body ≤ 16 KiB; demo page off by default and carries no secrets.
- Audit / observability: access log with route template only (AC-09).
- Idempotency / consistency: none on create (AC-04, see open questions). Status reads never write.

## 7. Threats & mitigations
| Threat (STRIDE) | Likelihood | Impact | Mitigation | AC |
|---|---|---|---|---|
| S: anonymous caller creates payments | M | M | Bearer token on `/v1` | AC-03 |
| I: customer reads another customer's payment (IDOR) | M | M | Ownership check; NOT_FOUND identical to unknown invoice | AC-07 |
| T: client picks a lower amount than the order's price | H | H | The client sends no amount; strict decoding rejects `amount` and per-item prices; the backend prices items from the catalog. The webhook also rejects a 2C2P amount that differs from the stored one (webhook AC-08) | AC-02, AC-12 |
| I: debug endpoint leaks another customer's events | L | M | Owner check through `GetPayment`; route exists only with `DEMO_UI_ENABLED=true` | AC-10, AC-13 |
| I: order/invoice numbers or tokens in logs | M | M | Route-template logging | AC-09 |
| E: demo page used to forge webhooks | L | H | Page disabled by default; it can only sign with a secret the operator pastes/passes in the fragment; the backend never serves the secret | AC-10, AC-11 |
| D: payment creation spam | M | L | Out of scope (gateway rate limiting) | — |
